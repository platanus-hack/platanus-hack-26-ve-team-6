External · source not required

DNS-verified public HTTPS origin

Customer proves domain control with a TXT challenge. The transport validates public DNS and TLS, then uses root-only consent or explicit bounded same-origin public discovery.

Choose internal, external, or both; each evidence stream keeps its own provenance and coverage.

Separate scanner service

Signed request · bounded profiles

HMAC-authenticated scanner boundary; the standalone service supports direct HTTPS and has no database or Redis access. The pinned Semgrep profile is 1.182.0.

Source lifecycle

Digest-bound snapshots

Immutable uploaded snapshots can be deleted once no queued or running assessment uses them.

Target lifecycle

Verified for seven days

Authorization expires after seven days. Renewal or revocation waits for outstanding assessments; uncertain scanner outcomes require operator reconciliation. Each application has one target.

How reports state evidence

Unknown remains unknown

Unsupported, missing, partial, or failed checks remain visible as unknown coverage. No finding is not a clean result.

Observations do not prove exploitation

Package matches and HTTP indicators do not prove reachability, deployment equivalence, exploitation, or compromise. Assessment does not exploit targets.

Assessment is observation-only.

Severity never grants action permission. Exact approval, provider writes, automatic response, and recovery are separate capabilities and are not enabled in this flow.

Monitoring and dashboard actions

Selected inputs

Scoped Git/GitHub snapshots, repeat npm advisory metadata, consented HTTPS checks and optional provider status feeds. Leased runs materialize canonical audits.

Private alerts

Signed runtime errors and supported suspicious behavior produce evidence-backed alerts. Healthy volume is not an attack; provider impact remains unverified.

Exact candidates

Versioned recipes and literal project context prepare a separate source snapshot and independent rescan. The original repository and production are unchanged.

Preparation has a concrete boundary

Capacity and migration checklists bind exact revisions. Self-reported steps do not enable production execution. Production action approval, provider adapters, behavioral validation and recovery remain separate gates; WebAuthn step-up code exists but is not a general approval path. Quotas and unknown coverage stay visible.

Runtime and remaining gates

Local development

Web at 127.0.0.1:3000, coordinator at 127.0.0.1:3003, scanner at 127.0.0.1:4400. Postgres, Redis, and data volumes are local; no customer seed is applied.

AWS is the planned host

Core contracts and adapters are portable. No AWS deployment, live AWS validation, hosted web ingress, or restore drill has occurred. The scanner's production-mode TLS path passed local Linux/amd64 checks before a CA PEM canonicalization correction; final focused reruns are pending.

Customer-code execution gate

The maintained Semgrep 1.182.0 profile ran through the production-mode scanner path before a CA PEM normalization correction; final focused reruns are pending. Broader accuracy and capacity validation remain open. Customer code stays disabled until disposable VM-class isolation is demonstrated.

Production controls remain open.

Production identity configuration and lifecycle, hosted web TLS ingress, recovery, provider-write authorization, broader scanner accuracy, and capacity evidence remain unproven or unavailable. WebAuthn step-up and tenant-scoped workspace invitation/member operations exist, but hosted validation and invitation email delivery do not.
