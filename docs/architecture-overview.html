Boundary:

Select any service to inspect its boundary. The existing customer WAF enforces its own rules independently. Customer teams retain incident response, merge, and deployment responsibility.

Mandatory scanner checks produce durable evidence. The agent investigates material results after those checks.

  1. Connect selected repositories

    A GitHub connection can produce an initial audit before the SDK, AWS, or Cloudflare is configured. Missing coverage remains visible.

  2. Commit audit intent

    The API writes the job and outbox entry to Postgres. The dispatcher sends the job ID through BullMQ.

  3. Scan an isolated snapshot

    The separate runner receives a fixed profile and scoped artifacts. It runs the mandatory scanner checks with deadlines and output limits.

  4. Record evidence and findings

    Validate and normalize scanner results. Bind evidence to the commit or configuration snapshot, tool version, collection time, checksum, and retention deadline.

  5. Investigate material findings

    An opted-in, budgeted LangGraph run reads actual evidence through the gateway. Limits produce an explicit delayed or inconclusive state.

  6. Show coverage and next actions

    The dashboard explains the issue, what was inspected, what is missing, and whether a supported correction can be prepared.

Coverage is part of the resultA repository-only audit can be useful immediately. Missing runtime events, cloud permissions, stale snapshots, and sampled WAF data remain explicitly visible.

Deterministic rules handle the event stream. The model receives selected incident evidence, rather than every incoming request.

  1. Receive signed event batches

    The customer Node application sends stable event IDs and bounded fields. The authenticated integration determines the organization.

  2. Persist before acknowledgment

    Validate and deduplicate events; commit them with outbox intent. Capacity and quota rejection is explicit, with bounded client retries.

  3. Group activity before using AI

    Aggregate by customer, application, detector, resource, actor context, and window. Versioned deterministic rules classify activity.

  4. Create or update an incident

    Keep blocked attempts, suspicious activity, and confirmed compromise distinct. Preserve evidence references and representative samples.

  5. Investigate and notify independently

    Material incidents can trigger the bounded agent. Deterministic detections and alerts continue when model work is unavailable or over budget.

  6. Expose the gaps

    Missing heartbeats, upstream sampling, delivery losses, stale connectors, and failed alert routes remain visible. Delivery is not acknowledgment.

Detection target: 30 seconds after acceptanceUpstream delivery delay is measured separately. Rejected batches and bounded-buffer losses create visible coverage gaps. The pilot does not provide automatic containment or staffed incident response.

Preparation happens before approval. Credentialed publication happens only after independent authorization.

  1. Prepare a narrowly allowed change

    The first adapter supports security patch and minor npm dependency upgrades with reproducible lockfiles. Preparation and customer tests run inside the disposable VM boundary.

  2. Validate the candidate

    An independent targeted rescan and a relevant configured test suite must pass at the proposed commit. Inadequate validation leaves an unverified patch.

  3. Freeze the exact proposal

    The server binds the patch, base commit, target, evidence, policy, tests, and verification plan into an immutable proposal and action hash.

  4. Obtain fresh human approval

    An authorized Owner approves that exact hash with fresh second-factor authentication. A nontechnical Owner can authorize PR creation.

  5. Recheck and publish independently

    The executor validates and claims the execution, checks current provider state and repository automation safety, then publishes the exact tested commit and PR. Observed base-head changes require new validation and approval.

  6. Reconcile and verify

    After uncertain timeouts, query provider state before retrying. Independently verify the PR and commit. The customer reviews, merges, and deploys.

A PR can trigger customer automationEnable PR writes only for supported repository automation configurations. If safety requirements or validation cannot be established, provide a reviewable patch without pushing a branch.

Two fixed servers are the reference layout. VM-class test isolation is an additional requirement whose deployment and cost must be demonstrated.

VPS A

Trusted control-plane services

  • Web app with Auth.js; HTTP adapter under review
  • Coordination, detection, and notifications
  • Restricted agent, read/model gateways
  • Independent approval and executor services
  • Postgres and persistent Redis / BullMQ

VPS B

Separate scanner environment

  • Trusted runner supervisor
  • Fixed static scanner profiles
  • Scoped input and result grants
  • CPU, memory, time, file, and output limits
  • No customer DB or provider credentials in jobs

Disposable job VMs

Required before running customer install scripts or tests

  • One-job lifetime, controlled network access, no production credentials
  • Hosted wherever the required isolation can be proven
  • The VPS reference does not establish nested virtualization support or cost feasibility

External storage and delivery

Private artifacts and encrypted backups live outside both servers. Model calls and email use external providers.

  • Proposed recovery: base backups plus continuous Postgres recovery data
  • Docker Compose deploys services; Pulumi TypeScript provisions infrastructure
  • Service boundaries on VPS A do not contain a complete host compromise
