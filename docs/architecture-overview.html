How reports state evidence

Unknown remains unknown

Unsupported, missing, partial, or failed checks remain visible as unknown coverage. No finding is not a clean result.

Observations do not prove exploitation

Package matches and HTTP indicators do not prove reachability, deployment equivalence, exploitation, or compromise. Assessment does not exploit targets.

Assessment is observation-only.

Severity never grants action permission. Private correction, independent validation and exact Owner approval are separate steps before an optional executor-created draft PR.

Monitoring, notifications and corrections

Selected inputs

Scoped Git/GitHub snapshots, repeat npm advisory metadata, consented HTTPS checks and optional provider status feeds. Leased runs materialize canonical audits.

Alerts and notifications

Signed events produce evidence-backed alerts and triage. Configured SMTP and signed HTTPS webhooks deliver notifications through a durable outbox with retries and visible status.

Private candidates

Versioned recipes and optional consented model workflows prepare private corrections and independent rescans. Each finding also offers a prompt to copy into a coding assistant.

Exactly approved draft PRs

The configured validator records signed base/candidate suite and rescan facts. After repository publication consent, the authenticated Owner approves the exact action without a second factor. The independent executor rechecks authority and repository freshness, publishes the draft and verifies remote state. Unknown outcomes require reconciliation.

Runtime and installation prerequisites

Local development

Web at 127.0.0.1:3000, coordinator at 127.0.0.1:3003, scanner at 127.0.0.1:4400. Postgres, Redis, and data volumes are local; no customer seed is applied.

Existing AWS installation

Core contracts and adapters are portable. The existing Lightsail host and its enabled services, TLS and encrypted backups are documented in the AWS runbook; optional services are not presumed enabled there.

Separate validation runner

Static scans execute no customer code. Supported base/candidate suites require the independently configured runner and its isolation gate. A selected-suite pass is not a full-suite or exploitability guarantee.

Implementation and availability are distinct.

Model credentials and consent, SMTP/webhook adapters, validation services and executor permissions determine which optional workflows are available. Future capabilities and outstanding operational verification are consolidated in the roadmap.
