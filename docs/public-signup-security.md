# Public signup: minimum safe configuration

Source review: 2026-10-24, base commit `016002f08c6b6d5933cd27bb7173c64e212613c8`, using gpt-6-astra. This is a repository review, not a live-host security or capacity assessment. The deployed Lightsail size, price, and hostname are supplied task context; no AWS/host changes or probes were performed.

## Recommendation

Add explicit `GOTCHU_AUTH_MODE=public` to enable the existing local account provider and anonymous registration in production. Keep `NODE_ENV=production`, the configured HTTPS origin, existing `AUTH_SECRET`, restricted API database login, and persisted database intact. Public mode must not depend on a setup token, invitation, manual approval, `GOTCHU_LOCAL_AUTH_ENABLED`, or the development registration flag. Preserve existing `self_host` and development behavior. This is sufficient for signup followed by creation of the user's own workspace, subject to the identity and availability limitations below; no identity migration or paid identity/email dependency is needed. [Runtime](../apps/web/src/server/runtime.ts), [auth settings](../apps/web/src/server/auth.ts), [account insertion](../packages/database/migrations/008_registration_admission.sql), [workspace creation](../packages/database/migrations/006_customer_applications.sql).

Keep `selfHostSetup` false in both Auth.js settings and the customer API for public mode: it currently gates sign-in and first-workspace creation. `/api/customer/setup` must return 404 in public mode, including when an old setup token remains in storage; the `/setup` UI should not offer bootstrap. Leave stored bootstrap records alone. The AWS service installer currently hardcodes `self_host`, so the parent's deployment configuration must also select public mode explicitly rather than silently reverting it during installation. This review does not authorize executing that installer. [Auth callbacks](../apps/web/src/server/auth.ts), [customer API](../apps/web/src/server/customer-api.ts), [setup page](../apps/web/src/routes/setup.tsx), [service environment](../infra/aws/install-services.sh).

## Security findings

1. **Signup does not grant access to existing tenants.** Credentials sessions use `credentials:<random account UUID>`, not email, as identity. Registration inserts only an account. Workspace discovery filters memberships by that principal; creation generates a fresh workspace ID and adds its creator as Owner. Customer operations authorize membership inside tenant-scoped transactions. Keep these boundaries unchanged; never attach accounts to existing memberships by email or choose the first workspace globally. [Auth JWT callback](../apps/web/src/server/auth.ts), [local accounts](../apps/web/src/server/local-accounts.ts), [workspace SQL](../packages/database/migrations/006_customer_applications.sql), [customer service](../packages/backend/src/customers.ts), [authorization](../packages/backend/src/core.ts).

2. **Local email is a claimed identifier, not verified identity.** The account schema has no email-verification state, and `accountEmail` returns the stored address. Anyone can reserve an unused email, preventing its legitimate holder from registering that address. They cannot thereby take an existing account or acquire its memberships. Do not describe this address as verified or introduce email-based account linking/recovery on that assumption. [Account schema](../packages/database/migrations/007_local_accounts.sql), [account lookup](../packages/database/migrations/022_members_step_up_alignment.sql), [account service](../apps/web/src/server/local-accounts.ts).

3. **Invitations rely on possession of the secret link.** Owners create 32-byte random tokens; only their SHA-256 hashes are persisted, invitation lists omit tokens, and acceptance requires an authenticated account, matching stored email, an unexpired/unrevoked token, and atomic single consumption. Invitation roles are Operator or Viewer, not Owner. However, an attacker who obtains an invitation token and can register its unused email can accept it: matching an unverified email is not a second identity proof. Email alone cannot discover or accept an invitation. Current UI explicitly asks owners to share the link with the intended person, and URLs put the token in a fragment. Retaining this explicit secret-link delegation is compatible with public signup; owners must treat links as credentials and share privately. If the product requires proof of mailbox ownership independent of link possession, the proposed mode alone does not provide that guarantee. No email-verification prerequisite is needed for creating a new private workspace. [Member service](../packages/backend/src/members.ts), [invitation SQL](../packages/database/migrations/019_workspace_members.sql), [HTTP adapter](../apps/web/src/server/members-api.ts), [sharing UI](../apps/web/src/components/members-panel.tsx).

4. **Conditional blocker: Google sign-in can be denied through email squatting.** The Google callback rejects a verified Google identity whenever an active local account has the same email. Public registration can therefore block future sign-ins to an existing Google account, even though it cannot access that account's memberships. The reviewed AWS installer supplies no Google credentials, so this is not a blocker for its credentials-only configuration; actual host configuration was not inspected. If Google is enabled, resolve this before enabling public registration there. Provider-subject identities must remain separate; neither automatically link them by email nor direct a Google user to an attacker-created password account. [Google callback](../apps/web/src/server/auth.ts), [installer configuration](../infra/aws/install-services.sh), [current auth expectations](../apps/web/test/auth.test.ts).

5. **Existing bounds limit work but permit public denial of service.** Registration admits ten valid-schema attempts per hour globally before hashing, including duplicates and requests later rejected by the two-derivation concurrency cap. Login allows 60 attempts/minute globally and five per email/15 minutes. State is persisted, but derivation concurrency is per service instance. Anyone can exhaust these shared quotas; same-origin checks prevent browser CSRF, not scripts that supply an Origin header. Preserve these bounds for the small initial change and describe temporary rejection truthfully; do not advertise ten successful registrations/hour or uninterrupted public availability. A later abuse-control change should preserve a global cap and use trusted ingress-derived client identity, never arbitrary forwarded headers. [Limiter and hashing](../apps/web/src/server/local-accounts.ts), [durable limiter SQL](../packages/database/migrations/007_local_accounts.sql), [single admission correction](../packages/database/migrations/008_registration_admission.sql), [origin checks](../apps/web/src/server/http.ts).

6. **Account creation is not an aggregate service budget.** Workspace creation stops at five current memberships per identity; application/assessment/source quotas are scoped to workspaces/applications. Multiple public accounts can multiply those allowances and accumulate persistent data over time. These controls do not demonstrate safe sustained capacity on a 4 GB host. Keep existing quotas and execution isolation gates; do not increase them as part of opening signup. [Workspace cap](../packages/database/migrations/006_customer_applications.sql), [assessment and source limits](../packages/backend/src/customers.ts).

7. **Reuse the real request/session safeguards.** Registration uses strict email/password validation (15–128 password characters), an 8 KiB JSON body limit, a body deadline, configured-host and exact-Origin checks. Credentials login uses Auth.js CSRF protection; HTTPS selects secure cookies, JWT sessions last 900 seconds, and credential epochs/disabled accounts invalidate sessions. Registration itself has no Auth.js CSRF-token exchange: its protection is JSON plus the exact-Origin check. No need to replace this path. [Customer API](../apps/web/src/server/customer-api.ts), [HTTP limits](../apps/web/src/server/http.ts), [local accounts](../apps/web/src/server/local-accounts.ts), [Auth.js configuration](../apps/web/src/server/auth.ts).

## Meaningful acceptance tests for the parent

- **Configuration matrix:** production + public exposes credentials and registration without either local flag; production default stays closed; self-host stays closed even with the development flag; existing development opt-in behavior remains unchanged. Missing database/auth secret never yields successful signup. Exercise runtime wiring, not only a helper predicate. Extend [runtime tests](../apps/web/test/runtime.test.ts).
- **Bootstrap separation:** public Auth.js sign-in and workspace creation work with no completed bootstrap, and neither calls `bootstrapComplete`; public setup POST is 404 even with a valid stored token. Existing self-host sign-in/workspace gates still hold. Extend [auth](../apps/web/test/auth.test.ts) and [customer API](../apps/web/test/customer-api.test.ts) tests.
- **Real signup lifecycle:** in isolated Postgres, register without invitation/setup token, perform an actual CSRF-protected credentials login, observe zero workspaces, then create and own one. A second account sees neither the first account's nor an existing deployment account's workspace/application/report/member/invitation data. Submitted user IDs/roles must not override session identity. Recreate the service and confirm accounts, memberships, and limits persist. Extend [local-account integration](../test/integration/local-accounts.test.ts) and [customer integration](../test/integration/customer-applications.test.ts).
- **Reject before mutation:** missing/foreign Origin, wrong request host, non-JSON, oversized body, malformed email, weak password, and extra fields cannot create an account; missing/invalid login CSRF cannot create a session. Verify case-normalized duplicate registration creates exactly one account under concurrency. Existing [HTTP](../apps/web/test/customer-api.test.ts), [auth](../apps/web/test/auth.test.ts), and [local-account](../test/integration/local-accounts.test.ts) tests are starting points.
- **Limiter boundary:** ten valid registration attempts consume the shared allowance and the eleventh returns 429 before account creation; duplicate attempts count; recreating the service does not reset it. Isolate/reset only disposable fixture limiter state. Keep epoch/disabled-account session invalidation coverage in [local-account integration](../test/integration/local-accounts.test.ts).
- **Invite trust boundary:** a public account claiming an invited email gains no membership without the exact token; another account's matching JSON email cannot override its stored email. Retain mismatch, expiry, revocation, replay, concurrent acceptance, and cross-tenant listing tests. If retaining secret-link delegation, document/test that token possession plus the claimed address can succeed without mailbox verification. Existing HTTP/Postgres tests already exercise acceptance by a freshly registered, unverified account: [HTTP invitations](../apps/web/test/member-invitations-postgres.test.ts), [SQL/service lifecycle](../packages/backend/test/members-postgres.test.ts).
- **Google only if enabled:** reproduce local email squatting against an existing Google principal; any fix must preserve that principal's access and must not grant the local principal its memberships. Current Google duplicate-email rejection expectations would need an intentional change, not deletion without replacement. [Auth tests](../apps/web/test/auth.test.ts).
- **Visible flow:** browser signup → sign-in → own workspace creation; errors stay usable; public `/setup` does not advertise token onboarding. Verify the existing account can still sign in. Keep deployment data/secret preservation separate from disposable test fixtures.
