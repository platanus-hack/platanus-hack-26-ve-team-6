# Paridad de capacidades: Snyk, Aikido y Gotchu

> **Actualización (24 de octubre de 2026):** esta matriz conserva la línea base del último commit del archivo, `fd668f7`. La afirmación de que Semgrep 1.90.0 sólo servía para desarrollo/pruebas y el gate asociado al scanner son históricos y quedaron superados para el alcance local Linux/amd64 validado: el perfil mantenido fija Semgrep 1.182.0 y las pruebas finales verificaron el flujo scanner/coordinator TLS y el trabajo durable. Esto no acredita despliegue cloud ni cobertura general. Véase el [registro de validación](validation.md) para la evidencia. No se actualizó la investigación comparativa de competidores.

Fecha de revisión: 24 de octubre de 2026. Se consultaron páginas oficiales de producto, ayuda, precios y documentación técnica de Snyk y Aikido en esa fecha. La comparación describe capacidades anunciadas por sus proveedores, no una prueba de calidad ni una auditoría de sus productos. Las funciones sujetas a plan, región o disponibilidad se señalan como tales.

Una capacidad de Gotchu sólo figura como implementada cuando existe una ruta de código y una prueba que ejercita el comportamiento. `parcial` significa alcance deliberadamente estrecho, bloqueado para producción o sin integración completa. `sin prueba` quiere decir que no encontré una prueba para la capacidad anunciada. El Semgrep actual es sólo de desarrollo/pruebas, por lo que no cuenta como SAST listo para clientes en producción.

## 3. Backlog de paridad priorizado

Ordenado para una empresa pequeña: primer resultado útil pronto, luego cerrar huecos de cobertura con riesgo alto. No presupone servicios pagados obligatorios.

## 4. Instalación y primer resultado hoy

### Desde una máquina limpia, en desarrollo local

1. Instalar Node 24, pnpm 11 y Docker con daemon disponible; reservar al menos 5 GiB de espacio Docker si faltan imágenes. No se ha verificado el flujo en todos los sistemas operativos.
2. Clonar el repo, entrar al checkout y ejecutar `pnpm install --frozen-lockfile`.
3. Ejecutar `pnpm dev:prepare` si faltan los perfiles fijados; descarga Semgrep, Gitleaks, Trivy, Postgres y Redis. Hace falta red y el script puede tardar.
4. Ejecutar `pnpm dev:start`. Crea `infra/.env` privado si no existe; genera credenciales locales, scanner secret, migra Postgres y crea roles. No se pide proveedor OAuth ni modelo.
5. Abrir `http://127.0.0.1:3000/dashboard`, registrar usuario local, iniciar sesión, crear workspace y aplicación.
6. Para interno: subir snapshot de archivos JS/TS, YAML/JSON/TOML y/o lockfile soportado. No hay ejecución de scripts. Ejecutar assessment y esperar la cola.
7. Para externo: confirmar autorización del origen, publicar TXT bajo `_gotchu.<hostname>`, verificarlo y lanzar evaluación. El perfil raíz hace una petición HTTPS; la superficie pública adicional requiere consentimiento.
8. Revisar informe, cobertura y recomendaciones. GitHub privado exige configuración operador-managed; la pantalla no añade integración por sí sola. Para Vigilancia, también se configura `GOTCHU_MONITORING_CONFIG_FILE` antes del arranque.

No se midió duración de la instalación ni el tiempo hasta el primer hallazgo útil. El UI ofrece formularios; no es todavía un onboarding guiado de dos clics. En un entorno sin imágenes puede ser necesaria la etapa lenta de preparación.

### Flujo objetivo

Un solo comando/instalador local debe verificar requisitos, generar secretos locales seguros, iniciar servicios y abrir una pantalla de bienvenida. El Owner crea el workspace y puede **subir carpeta/archivo** como primer camino sin OAuth, nube ni dominio; elegir “Escanear”; obtener el reporte y 1–3 recomendaciones. Ruta de repositorio es una conexión posterior. La fuente externa pide consentimiento y ownership, con resumen de scope antes de iniciar. Un segundo flujo ofrece “Crear incidente” sólo a partir de evidencia/señales observables, solicita autorización de fuente antes de investigar y mantiene todo en modo observación hasta una aprobación explícita.

Para ofrecer este flujo hacen falta pruebas E2E de clean install, estado vacío, carga, errores recuperables, primer informe y primer incidente; mediciones reproducibles en hardware documentado; empaquetado y actualización; bootstrap seguro de Owner; TLS/secret custody para instalación expuesta; migración/rollback; backup/restore ensayado; y cobertura scanner production. “Un par de clics” se debe usar como claim sólo después de que el camino medido lo cumpla.
