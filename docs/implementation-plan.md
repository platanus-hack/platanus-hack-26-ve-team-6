# Implementation status and release gates

## Current stage

The current product is an authenticated local application for source/public HTTPS assessment, selected-input periodic monitoring, signed runtime alerts and exact private correction preparation. Its usable customer path includes local account registration and sign-in, workspace creation/listing, application create/list/rename/archive/restore, source snapshot upload/deletion, DNS TXT target verification/expiry/revocation, queued assessments in three modes, and persisted evidence-backed reports.

The fictional vulnerable/corrected application is a regression fixture only. The customer flow does not depend on a demo seed, fixture tenant, or fixture revision. The development runtime is local only; AWS is the planned primary hosting target, and no cloud deployment has occurred.

For the detailed next-stage backlog, dependencies, acceptance checks, and evidence-based comparison with Snyk/Aikido, see the [autonomous defense and differentiation plan](plan-defensa-autonoma.md). Its proposed capabilities remain pending; this document records implemented behavior and release gates.

## Architecture and boundaries

TanStack Start adapts HTTP requests to Auth.js and framework-independent backend services. The authenticated server session supplies the user identity; client-provided organization/application IDs are selectors, not authorization. Membership checks and Postgres row-level security scope customer operations. The API writes only its allowed database role.

Postgres is the authority for assessment requests, leases, source snapshots, and reports. The outbox feeds Redis/BullMQ, and the independent coordinator claims work. It passes the durable request to the separate scanner service over the signed HTTP boundary. The scanner has no database or Redis access. It returns a contract-validated report; the backend rechecks lease, source digest, and target authorization before committing report and job completion.

The internal and external profiles run independently. Internal scanning is source-only and never executes customer code. External assessment can run without any source upload. `both` combines their evidence while preserving which observations came from each profile. The Helmet CSP gate accepts only two fixed Semgrep IDs and parses with TypeScript 5.9.3 `createSourceFile`; it does not resolve modules, transpile, or execute source. It requires a unique value import, matching call location, and literal configuration, then applies conservative whole-file conflict checks. A shared CSP group describes observations about the same control, not proof of the same issue, deployment, cause, or exploit. Unknown coverage remains unknown and is never converted into absence or a clean result.

Target renewal/revocation waits for settled work: queued/running requests return 409 without changing authorization. An uncertain scanner/transport outcome or reclaimed customer delivery is quarantined for trusted operator reconciliation, rather than automatically rescanned. That quarantine continues to block target changes after the job is marked failed; no customer HTTP escape is exposed.

AWS is the intended first hosting provider, while core domain contracts and adapters remain replaceable. Infrastructure definitions or local service tests are not evidence of a live AWS deployment.

## Local commands

The customer development launcher uses Node 24, pnpm 11, Docker, and `scripts/development.mjs`:

```sh
pnpm dev:prepare
pnpm dev:start
pnpm dev:stop
```

`dev:prepare` prepares the pinned local scanner and data-service images. `dev:start` builds the required packages, checks local configuration and image availability, starts Postgres/Redis, and then starts web, coordinator, and scanner after readiness succeeds. It creates no customer or demo seed. `dev:stop` stops only the recorded application processes; local data services and persistent volumes remain. Use [local development instructions](development.md) for preparation requirements, configuration, port overrides, and data-service shutdown.

Workspace checks, integration runs, and their actual results are tracked in the [verification record](validation.md). Do not treat a test source or mock test as a test run, live AWS check, production scanner validation, recovery drill, or service guarantee.

## Monitoring and correction milestone

Implemented: persisted monitor configuration/runs/leases and scheduler/check liveness, scoped operator repository catalogs, exact Git/GitHub snapshots, repeat OSV metadata checks, Cloudflare/Railway public status context, explicitly consented bounded public discovery, signed telemetry key lifecycle, versioned runtime detectors, durable workspace email/webhook delivery with a Postgres outbox, private alert triage and revision-bound advisory plans. The Node SDK also has opt-in sink wrappers for four runtime attack patterns, signed policy and event paths, per-application configuration, and the customer protection panel. This is narrow instrumentation, not broad process-wide protection; see the customer path table and SDK README for the covered sinks and limits.

Supported exact TLS/configuration corrections create separate private source candidates and atomic rescan jobs. Context and findings select versioned recipes; there is no model-generated arbitrary command execution. The original repository and production remain untouched. Dependency upgrades, credential rotation, broad source rewrites and provider actions require additional adapters/validation.

D05 adds versioned per-repository suite configuration, an atomic validation record on correction preparation, and a separate `@gotchu/validator` worker. It builds runner archives only from private stored base/candidate snapshots, checks the approved base and candidate digests, and records signed, immutable attestations for base reproduction, candidate regression, functional counts, and independent base/candidate rescans. Scanner failures, incomplete coverage, modified tests/scripts, a closed runner gate, or missing reproduction evidence remain inconclusive. Deleting tested functionality fails the VM suite. The public correction status projection keeps “reanálisis objetivo” and “suite” facts separate. The current runner only supports the `node24-npm-test` profile and `npm test`; custom scripts and fuzzing are not implemented.

### Versioned actions and approval flow

Action v2 is a strict discriminated union for dependency PR, source patch PR, merge, deploy, rollback, and provider response. The proposal ledger stores version, kind, capability, lifecycle state, and public blocking reasons; the action hash binds canonical action JSON to the recovery epoch. Existing v1 proposals keep their original schema and hash. Recovery increments invalidate open proposals. A base change observed by the independent action verifier invalidates that proposal as well.

The customer API exposes tenant/application-scoped action list, detail, propose, eligibility, approve, reject, and cancel operations. Propose accepts only a private correction candidate reference; the server reads candidate/audit records and resolves the single active repository link. Public detail contains a sanitized path/summary, never source content. Owners approve eligible exact hashes through the existing WebAuthn helper. The UI separates validations, shows unknown cost and blockers, and distinguishes PR, merge, and deployment approvals. Current v2 proposals remain ineligible: this runtime has no v2 VM verifier, source validation attestations, or write adapter. Executor ledger parsing recognizes v2 structurally and fails with `no_adapter` before consuming an approval. No v2 provider writes are enabled.

The action state vocabulary is `proposed`, `eligible`, `ineligible`, `approved`, `expired`, `invalidated`, `executing`, `succeeded`, `failed`, `uncertain`, and `reconciliation_required`. `succeeded` records an executor result; the interface still describes it separately from independently verified application outcome. D08 artifact/VM validation and executor lifecycle, D09 real repository PR writes and race handling, and D10 merge/deploy/rollback adapters and verification remain release gates.

### D08/D09 implementation status

This branch adds a strict `ValidationFactsPort` seam to the independent action verifier, private candidate digest checks, current-base reads, and durable per-attempt state rows in migration 023. The web runtime currently binds validation facts to `null`; until D05 is integrated, real actions remain ineligible with `validación en VM no disponible`. `source_patch_pull_request` also lacks an approved base SHA in its current action contract and is explicitly refused at approval.

`@gotchu/git-adapters` provides local bare-Git support and a GitHub App adapter with short-lived token caching, response schemas, deterministic branches, workflow trigger checks, conditional ref creation, duplicate-publish reconciliation against tree/parent, PR lookup by branch, and reconciliation after an ambiguous PR response. The final opt-in sandbox provider test created and closed PR #8; all earlier test-created PRs (#1–#7) were also closed and their branches deleted. The adapter is not yet wired to an executor service or D05 candidate artifacts; the web runtime also lacks a policy registry and workflow reader, so both checks remain fail-closed. These checks do not enable product writes.

## Application context inventory

Implemented in migrations 014 and 016: tenant-scoped environments, services, repository links restricted to the configured repository catalog, deployments, dependency relations, and origin candidates. Writes are limited to owners/operators, audited, rejected for archived applications/environments, and bounded per application/environment. Customer declarations always remain `declared` with source `customer_declared`; customer requests cannot set `verified`, `operator`, or `signed_telemetry`. Repository read access follows catalog membership and becomes revoked on revoke; write access remains `not_granted`. Origin ownership is accepted only as `unknown` or `claimed`; `verified` is derived at read time while its linked target is DNS-verified and unexpired. An origin candidate does not authorize assessment. Signed event attributes may include bounded release, service, dependency, and templated route values. These attributes are not yet materialized into deployment rows because event labels alone do not identify a verified service or prove deployment contents. Analyzed versus deployed identity is shown as match/difference only for verified deployment state with a shared commit or source digest; otherwise it remains unknown.

Monitoring shares finite assessment/source admission and has retained-run/observation/plan bounds. Operator retention maintenance is still required. Notification delivery is at least once with bounded retries; it is not a human-read guarantee, and a full coordinator outage delays external delivery until a worker returns. Provider status evidence has unverified application impact. Actual setup and button behavior are documented in [operations](operations.md); test results belong in [validation](validation.md).

## Incident triage milestone

Implemented locally: tenant/application-scoped incidents and immutable, digest-deduplicated triage revisions; durable coordinator evaluation after every accepted signed-event batch; verified/declaration-aware context; owner/operator incident status with SQL and service authorization; and a Spanish incident card with impact, hypotheses, evidence, unknowns, and revision history. Grouping selects the latest non-closed incident for an application/environment with evidence in the prior two hours; after two quiet hours a later evaluation opens a new incident. User closure immediately removes that incident from grouping and affects triage status only, never inferred impact.

Connected triage inputs: Cloudflare/Railway observations recorded by monitoring are schema-checked and stored with observed time and fixture status. Cloudflare global status stays global; current component observations stay component-scoped. The current providers do not supply regional observations, so none are inferred. Existing observations without structured scope remain global. Signed event attributes label metrics only when their referenced request sample is complete and names a known application service; the environment comes from that service's inventory. Incomplete or unknown labels remain application-level and produce missing-baseline coverage. HTTPS results use the existing verified target and fixed same-origin paths allowed by its scan profile. Owner/Operator declarations identify route role, service, and an existing D01 dependency; these declarations never add targets. The UI labels them as declared.

The coordinator schedules a durable triage projection after event aggregation. Its metric series use the latest signed event time, with a rolling 30-minute evidence window; stored deployment timestamps are normalized before contract validation. Separately, a fixed ten-minute runtime-metric window retains its first immutable metrics snapshot while later batches recompute detectors against the expanded event window. Authentication-only detection, quota handling, and rollback behavior remain covered. This does not continuously refresh metrics within the same window or establish a recovery measurement. Incident retention runs only through a bounded `gotchu_owner` security-definer function that audits whole-incident deletion. Reaching incident or revision bounds degrades the triage projection without rolling back accepted detections. While the incident page is visible, the list and each incident detail poll every ten seconds for newly persisted incidents and revisions.

Live Postgres/Redis coordinator tests cover the §9 provider-incident/app-healthy, verified-release/error-rise with an alternative traffic hypothesis, and provider/dependent-route/control-route situations, plus stale telemetry and incident/revision bounds. They use real HMAC intake, an explicitly marked Cloudflare fixture feed, and the HTTPS adapter against a local TLS fixture. Real provider feeds, regional feed evidence, production operation/capacity, full D15 precision/recall and false-positive measurements remain absent. Evidence requests only advance the due time of the already-enabled monitor; they do not add targets or promise report execution completion.
