# Customer assessment engine (development)

`createCustomerAssessmentRunner(options?).run(input: CustomerRunInput): Promise<CustomerAssessmentReport>` accepts the exact version 2 `@gotchu/contracts` input returned by `backend.customers.getRequest(claim)`. It assesses uploaded customer files, a bounded container image, and/or the independently verified public HTTPS origin. There is no demo target, fixed repository or revision enum. Reports bind organization, application, job, source or image digest and target ID/version/origin. Persist through `backend.customers.recordResult` to recheck the lease and current authorization.

```ts
import { createCustomerAssessmentRunner, createOsvAdapter } from '@gotchu/customer-assessment';
const runner = createCustomerAssessmentRunner({ advisory: createOsvAdapter() });
const readiness = await runner.readiness();
const report = await runner.run(persistedInput);
```

`CustomerAssessmentOptions` accepts optional trusted `scanners: ScannerAdapter`, `advisory: AdvisoryAdapter`, `https: HttpsOptions`, and `deadlineMs` (1–55,000; default 55,000). These are operator/test adapters, never HTTP input. Omitting the advisory adapter makes advisory coverage unavailable and readiness unready; deterministic source/HTTPS checks still run. Source and external branches run independently. External-only needs no repository, source, scanner image or advisory API.

## Profiles and evidence

Source bounds derive from the shared contract: 4 MiB serialized snapshot, 1,000 files and 1 MiB per file. The runner verifies the canonical source digest used by the backend (sorted object keys, ordered files). It never installs packages, imports customer modules, runs scripts/tests/build tools, or executes customer code.

- Semgrep CE 1.182.0 runs the vendored, repository-maintained rule pack v1.0.0 in `profiles/semgrep.yaml`: selected JS/TS, Python, Go and Java rules. Each rule records a stable ID, CWE, OWASP category, severity and precision note. The rules are original Gotchu rules under MIT; `profiles/semgrep-rules/README.md` records the scope and why Semgrep Registry rules are not redistributed. Live positive and corrected controls exercise each language. Matches are static indications, not taint or reachability proofs. The separate Helmet CSP candidate still requires the fixed TypeScript 5.9.3 parser gate described below; it rejects ambiguous call structure and nested scopes. Metrics/version checks, git ignores and inline suppression are disabled. An empty controlled `.semgrepignore` replaces default exclusions. Parse errors, omitted supported files, or unsupported CSP candidates yield unknown coverage.
- Gitleaks 8.28.0 uses the full upstream default configuration pinned from the v8.28.0 tag in `profiles/gitleaks.toml`; the upstream MIT license is included next to it. Full CLI redaction is preserved; source excerpts and secret values are never retained in reports. A match does not verify whether a credential is valid, active or revoked. Customer suppression/configuration cannot override the fixed profile.
- Trivy 0.67.2 runs its embedded Kubernetes, Terraform and Dockerfile configuration checks. Kubernetes candidates are classified by `apiVersion` and `kind`; malformed candidates stay unknown. Terraform files and Dockerfiles are accounted for independently. Helm templates are not rendered, hooks are never run, and Terraform is never executed. No remote checks or customer configuration are fetched. Missing candidate results make that candidate's coverage unknown.
- Container images: accept an uploaded `docker save`/OCI archive up to 8 MiB or an exact `@sha256:` digest from the public registries Docker Hub, GHCR, Quay, public ECR or `gcr.io`. Credentials and private registries are unsupported. An uploaded archive is stored tenant-scoped and scanned as bytes; a registry image is pulled by immutable digest using an empty Docker auth configuration. The image is never started. Trivy scans OS and language package CVEs in image mode, reports fixed-version and available layer/digest evidence, and records the pinned profile and DB provenance. Trivy's main vulnerability DB is refreshed outside scans by `scripts/update-trivy-db.mjs`: the helper resolves the public OCI tag to an immutable manifest digest, downloads only that artifact, and writes a SHA-256 lock with its metadata timestamp. Scans use the cached DB with no network and fail closed if its checksum is invalid, changes during scanning, or it is older than 14 days. Trivy requires write access to its Bolt DB, so only the isolated scanner UID can write the mounted database directory. The Java index DB is intentionally not downloaded, so Java package CVE coverage remains unknown. Unsupported or unrecognized distributions and ecosystems remain unknown too.
- npm `package-lock.json` v2/v3, pnpm lock v6/v9, and Yarn classic/Berry: bounded direct/transitive exact-version inventories. At most 2,000 lock entries and 1,000 package components are retained; unsupported/ranged entries, formats and excess packages stay unknown. The optional OSV adapter makes at most two batches of 100 queries to `https://api.osv.dev/v1/querybatch`; only package names and versions leave the host. No source, tenant IDs, credentials or lockfile contents are sent. Each response is capped at 256 KiB with an eight-second deadline; redirects/compression are refused. Pagination stays unknown. Querybatch returns advisory IDs, not severity: reports explicitly mark severity unassessed and exploitability unknown.
- JS/TS reachability: the TypeScript parser looks for ESM imports, re-exports, literal dynamic imports, and literal `require()` calls, including package subpaths. It reports `reachable` only when an OSV-provided affected symbol is also referenced, `imported` when import evidence exists without that symbol evidence, and `not_found_static` when no supported static import was found. The latter is not an unreachable verdict. Nonliteral runtime resolution, parse errors, unsupported aliases, missing OSV symbols, and transitive packages without a complete lockfile path remain explicitly unknown. This is not a call graph or runtime analysis.
- Exact npm artifacts: at most three highest-priority vulnerable packages per assessment are fetched from `registry.npmjs.org` with fixed time, byte, and origin bounds. SHA-512 lockfile integrity is checked before extraction; mismatches are reported without scanning the contents. The in-memory tar reader rejects traversal, links, unsupported entry types, duplicate paths and excessive compressed/decompressed size, ratio, file count or scanned text. No install hooks run. Existing Semgrep/Gitleaks profiles scan only bounded source/config files and findings are scoped to `package@version:path`. Missing lockfile integrity, omitted files, scanner errors and cap hits remain visible as incomplete coverage. Maintainer Git `main` is not compared with the registry artifact.

Each profile records its image digest, tool version, controlled-rule checksum, source digest and bounded redacted evidence with SHA-256 checksums. Semgrep profile provenance also records the Helmet gate version and actual TypeScript parser version. The source CSP finding is a static configuration indication only: registration, execution, other CSP mechanisms, deployment, route association, causality and exploitability remain unknown; it does not raise the existing inferred confidence or medium Semgrep severity. At most 100 findings/200 evidence records per analysis and 1 MiB per report; omissions make coverage partial. Source/deployment equivalence and absence in the other analysis are unverified. Package/advisory matches and banners never prove exploitation or compromise.

Customer reports include the profiles that ran and one coverage entry per capability. `unsupported` means no candidate was present; `unavailable` means a candidate could not be inspected or the required DB was unavailable; neither state is shown as clean. Image reports keep OS, language and Java DB coverage separate.

## Trusted local scanner host

The supervisor needs Docker CLI access to the local Unix daemon. It has no database/Redis dependency. Images are fixed in `src/docker.ts`; pull them as an operator before readiness, never during a job:

```sh
docker pull semgrep/semgrep@sha256:4a34048c04fef049f71665047f074cffb00cc3d89482f965a5cd151d589237af
docker pull zricethezav/gitleaks@sha256:cdbb7c955abce02001a9f6c9f602fb195b7fadc1e812065883f695d1eeaba854
docker pull aquasec/trivy@sha256:e2b22eac59c02003d8749f5b8d9bd073b62e30fefaef5b7c8371204e0a4b0c08
```

The scanner requires a verified Trivy DB directory configured by `GOTCHU_SCANNER_TRIVY_DB_DIRECTORY` for image CVE assessments. `pnpm dev:prepare` refreshes the local `.local/dev/trivy-db` cache. The refresh helper is the only network-enabled DB operation; customer scanner containers run with `--network none`. Trivy requires write access to its Bolt DB even with updates disabled, so only the isolated scanner UID can write the mounted DB directory; the SHA-256 is verified before and after each image scan. The default vulnerability DB is pinned by resolved OCI digest and database checksum, with a 14-day freshness limit. The optional Java index is not downloaded because it is substantially larger; Java package CVE coverage is reported unknown.

Every job has a private temporary parent directory, validated files mounted read-only, a fixed read-only profile, nonroot UID, no network, no capabilities, no-new-privileges, read-only root, 128-process limit, one CPU, 30-second CPU limit, 768 MiB memory/no extra swap, 128 MiB noexec tmpfs, 1 MiB combined stdout/stderr bound for source profiles and 4 MB for bounded Trivy image JSON, and a 35-second wall deadline. Docker daemon logging is disabled. The service credential is absent from the CLI environment and scanner containers. No Docker socket is mounted into a scanner. No shell interpolates customer text. Finally blocks remove the exact named container and directory; cleanup failure fails the job and latches the adapter and runner unready. The engine promise retains ownership until every started operation, including cleanup, settles, even after cancellation. A hung adapter cannot release capacity by reaching its deadline. Cleanup faults never become partial-success reports. Failed container removal retains its private directory for reconciliation; the operator must confirm removal of the affected containers/directories before restarting the supervisor. There is no automatic fault reset. These are parser sandboxes, not demonstrated VM isolation; customer-code execution remains prohibited.

Readiness actually runs the pinned profiles against known self-test bytes and requires real matching output; image existence alone is insufficient. Results cache for 30 seconds and process failures invalidate the cache. Aggregate readiness also coalesces and caches the advisory check for 30 seconds. The OSV adapter readiness checks an actual bounded query when enabled. Missing/broken tools return unready and unavailable coverage.

## Public HTTPS transport

The default `root` scan profile, including older durable requests with no profile field, makes one GET `/` at the persisted canonical HTTPS origin, port 443 only. The selected `public_surface` profile keeps that same target origin and makes a fixed, bounded set of serial GETs: `/`, `/.well-known/security.txt`, `/security.txt`, `/robots.txt`, `/sitemap.xml`, then uses any remaining slots up to ten total for same-origin links extracted from bounded HTML anchors and sitemap locations. It also follows same-origin `Sitemap:` entries from `robots.txt`. Paths with a query or fragment, traversal, a different host/scheme/port, or unsafe URL syntax are ignored. Neither profile follows redirects, sends credentials/cookies, retries, enumerates subdomains or exploits the target.

Both profiles resolve all DNS addresses afresh for every request and reject any nonpublic, mapped, metadata, multicast, reserved or documentation address. A selected validated IP is pinned to the socket; TLS verifies the certificate chain and requested hostname with SNI. Domain ownership is not independently proven; scope comes from the signed-in user’s Analyze request. The deadline for each request is the earlier of five seconds or the target scope expiry. Scope expiry is checked again immediately after DNS before any connection; a delayed DNS answer cannot authorize a late GET. Each response has an 8 KiB raw header limit and 16 KiB streaming body limit. The `public_surface` profile also limits the full run to 64 KiB of response bodies and waits 250 ms between requests. Bodies/cookies/location headers are discarded from report evidence. Missing headers are observations for that response; banners are unverified indications, never inventory.

The exported `createPublicSurfaceProbe` requires a validated target with `scanProfile: 'public_surface'`; it returns a typed inventory of the exact requested origin and entrypoints. The runner selects it only when that explicit persisted profile is present. Missing/`root` profile values stay on the one-request legacy path. The report records response summaries and coverage in the existing report schema. Hitting a cap or losing transport preserves completed responses and marks the remaining coverage unknown. This profile is not a company-wide asset inventory: JavaScript-generated, authenticated, query-based, subdomain, non-HTTPS and alternate-port entrypoints remain outside coverage.

`HttpsOptions.testFixture` is accepted only with `NODE_ENV=test`, an injected lookup, an exact fixture hostname, a nonprivileged explicit port and a supplied test CA. Only that fixture can use literal loopback answers. It cannot grant production private-network access. DNS/TLS/body/header failures remain unknown.

## Verification and limits

After the parent integrates version 2 contracts and reconciles the shared lockfile:

```sh
pnpm --filter @gotchu/contracts build
pnpm --filter @gotchu/customer-assessment build
pnpm --filter @gotchu/customer-assessment typecheck
pnpm --filter @gotchu/customer-assessment test
pnpm --filter @gotchu/customer-assessment test:live
```

Unit tests include explicitly injected unavailable scanners/advisory fixtures. HTTPS tests use real sockets and a temporary self-signed certificate generated with OpenSSL, scoped to the test hostname/port. `test:live` requires Docker and outbound OSV access and fails if unavailable; it executes all three pinned scanners and the live advisory query. It does not silently skip or manufacture findings.

The maintained Semgrep 1.182.0 profile is digest-pinned and has passed local Linux/amd64 Docker validation, including a `NODE_ENV=production` TLS scanner-to-coordinator run that persisted a tenant-bound, source-bound report and delivered its outbox record. Gitleaks, Trivy, and OSV were exercised against the documented bounded profiles. This evidence does not establish broad scanner accuracy, all-architecture behavior, AWS deployment, VM isolation, general route scanning, installed inventory, exploitability proof, or production capacity. No customer code is executed.

Official references consulted: [Semgrep CLI](https://docs.semgrep.dev/cli-reference), [Semgrep Docker images](https://hub.docker.com/r/semgrep/semgrep), [Gitleaks configuration and redaction](https://github.com/gitleaks/gitleaks), [Trivy config CLI](https://trivy.dev/docs/latest/references/configuration/cli/trivy_config/), [OSV batch API](https://google.github.io/osv.dev/post-v1-querybatch/).

Source assessment remains intentionally bounded to uploaded JS/TS, JSON, YAML, and TOML files. Dependency inventory supports the formats listed above; unsupported manifests, package formats, excess entries, and unrecognized configuration coverage remain unknown. The scanner's standalone production TLS configuration and coordinator-scoped CA trust are documented in [the scanner service guide](../../apps/scanner/README.md). Local production TLS and source-report checks passed for the exercised Linux/amd64 paths; representative accuracy and capacity validation remain open.
