# Backend integration contract

Framework-independent services for TanStack Start/Auth.js, trusted coordinators and gateways, and the independent executor. Libraries build ESM into `dist` using the root TypeScript settings. Build contracts and database before backend.

```ts
import { createDatabase } from '@gotchu/database';
import { createBackend } from '@gotchu/backend';

const database = createDatabase({ connectionString: runtimeUrl, role: 'gotchu_api' });
const backend = createBackend({ database }); // Approvals disabled until trusted verifiers are injected.
await database.checkHealth(); // Verifies restricted runtime login; needs no customer selector.
```

Use separate runtime logins and backend instances for `gotchu_api`, `gotchu_ingest`, `gotchu_coordinator`, and `gotchu_executor`. Database permissions constrain each instance even though `createBackend` returns the same service interface. Never use an operator/migration connection at runtime. The investigation process gets neither this backend object nor a database connection: expose only a run-scoped authenticated gateway to it.

## HTTP adapter contract

### Controlled assessment integration

`backend.assessments` uses the shared `AssessmentRunInput` and `AssessmentReport` contracts. These are observation-only controlled checks; reports never grant verified remediation or action permission.

- `queue(identity, { organizationId, applicationId, mode, revision, idempotencyKey }): Promise<{ jobId: string }>` authorizes Owner/Operator membership, selects the operator-enabled target, and commits request, audit job, outbox and audit record together. Reusing a key with another mode, revision or configured target fails with `idempotency_conflict`.
- `getTarget(identity, { organizationId, applicationId }): Promise<{ targetKey: string } | null>` authorizes membership and returns the enabled opaque target key, never a URL or filesystem path.
- `list(identity, { organizationId, applicationId, limit? }): Promise<AssessmentReportSummary[]>` returns at most 50 report summaries (default 20).
- `get(identity, { organizationId, applicationId, reportId }): Promise<AssessmentReport>` authorizes membership and loads one validated report. Use `web.getJob` to poll jobs; successful assessment jobs expose `reportId`.
- Coordinator only: `getRequest({ organizationId, applicationId, jobId, leaseToken }): Promise<AssessmentRunInput>` checks the current audit-job lease, persisted request, job payload, and enabled target before returning trusted runner input.
- Coordinator only: `recordResult({ input: AssessmentRunInput, leaseToken: string, report: unknown }): Promise<{ reportId: string }>` validates the report, checks input/report/request scope and the enabled target, and stores the report plus job completion in one transaction under the current lease. Both serialized report JSON and stored JSONB text are bounded at 1 MiB. Expired/replaced leases roll back all effects.

Targets are operator-managed rows in `gotchu.assessment_targets`; API/coordinator roles can only read them. Each app has at most one enabled target. To change it, disable the previous row and enable a new key in one operator transaction. Existing requests retain their original key and cannot be redirected. No request accepts a target URL/path/key. The adapter resolves `controlled-demo-store` to its operator-configured fixtures and HTTP origin.

The operator-only `node scripts/assessment-demo-seed.mjs` uses `GOTCHU_MIGRATION_DATABASE_URL` after package builds. It creates only `DEMO_ASSESSMENT_SCOPE` (exported by backend) and the fixed `DEMO_ASSESSMENT_TARGET_KEY`. It is repeatable and refuses conflicting existing scope/configuration instead of overwriting it. The migration/operator login must see all rows; runtime credentials are insufficient. The reserved `demo:controlled-assessment` principal is deliberately public, not an authenticated customer identity. Generic backend operations deny it; only assessment operations and job polling for the fixed app accept it after membership checks. The public HTTP adapter must be opt-in, enforce origin/body/usage bounds, inject this fixed scope, and call these same membership-authorized assessment methods. Never accept that principal from a customer session or expose operator credentials at web startup.

The fixed scope is organization `d3e00000-0000-4000-8000-000000000001`, application `d3e00000-0000-4000-8000-000000000002`, user `demo:controlled-assessment`, with target `controlled-demo-store`. Its queue transaction permits at most three unfinished audit jobs and 100 total audit jobs, serialized under the target lock across API instances. Exact idempotent retries return before quota checks. New work fails with HTTP 429 `assessment_capacity_exceeded` or `demo_assessment_limit`; the lifetime bound requires deliberate operator cleanup in a disposable demonstration environment. These are admission bounds, not measured throughput guarantees.

Legacy `web.queueAudit` jobs contain no assessment request and remain visibly unavailable to a configured runner. New assessment HTTP adapters must use `assessments.queue` and the explicit mode/revision contract.

`backend.events.ingest({ integrationId, timestamp, signature, rawBody })` takes the exact received Buffer. `MAX_EVENT_BODY_BYTES` is 256 KiB; enforce it while streaming, before buffering. At most 100 events fit the shared `eventBatchSchema`. The integration supplies the organization and application; `signed_events` only accepts `source: 'application'`.

HMAC-SHA256 input is the UTF-8 prefix `gotchu-events-v1\n${integrationId}\n${timestamp}\n`, followed by the exact raw bytes. Timestamp is decimal Unix seconds within 300 seconds of server time. Signature is 64 lowercase hex characters. `signEventBody` and `verifyEventSignature` are exported. `CredentialStore.getSigningSecret(reference): Promise<Uint8Array>` must resolve at least 32 secret bytes from an external secret store or encrypted adapter; the database only stores an opaque reference in the intake-only credential table.

The response is `{ accepted, duplicates, jobId: string | null }`. Stable event IDs deduplicate per integration; changed event content rejects the entire batch. UUID spelling is normalized; object key order is immaterial. A response is returned only after the event, durable job, outbox, and audit transaction commits. A repeated batch returns zero accepted and `jobId: null`. These body/batch bounds are not measured sustained-rate or per-tenant quota guarantees.

Customer web methods take `identity: { userId: string }` exclusively from a trusted server-side Auth.js session (for example `github:<providerAccountId>`). The fixed public assessment demo above is a separate, explicitly restricted entry point. Organization IDs select a tenant; every method checks membership inside the transaction. Cookie-authenticated routes must enforce same-Origin/CSRF protections in the web adapter. Domain services do not consume identity headers.

- `web.authorize(identity, organizationId, roles?)` returns `owner | operator | viewer`.
- `web.listApplications(identity, { organizationId })` returns `{ id, name }[]`.
- `web.queueAudit(identity, { organizationId, applicationId, idempotencyKey })` returns `{ jobId }`; Owner or Operator only.
- `web.getJob(identity, { organizationId, jobId })` returns `{ id, applicationId, kind, state, attempts, createdAt, completedAt, outcome, reasonCode, reportId }`. Payload and private checkpoints are excluded; `reportId` is null before successful assessment completion.
- `web.listIncidents`, `web.getCoverage`, and `web.listProposals` take `(identity, { organizationId, applicationId })`. Lists are bounded at 100. Coverage synthesizes explicit unconfigured/unsupported states; customer-code execution is unsupported until a separately verified VM boundary exists.

Expected failures are `BackendError` with `code` and HTTP `status`. Invalid runtime contracts fail as `invalid_input`. Do not expose unexpected database/credential/provider exception details in HTTP responses.

## Coordinator contract

The scheduler supplies trusted organization IDs; there is no global customer enumeration endpoint.

- `outbox.claim({ organizationId, limit?, leaseMs? })` returns `{ id, envelope: JobEnvelope, leaseToken, leaseUntil, attempts }[]`. Publish `envelope` with its stable job ID, then call `outbox.delivered({ organizationId, id, leaseToken })`. A crash after publish may deliver the same job again.
- `jobs.claim({ organizationId, jobId, leaseMs? })` returns `{ envelope, payload, leaseToken, leaseUntil, attempts } | null`. Null means already completed or currently leased. `jobs.heartbeat({ organizationId, jobId, leaseToken, leaseMs? })` and `jobs.complete({ organizationId, jobId, leaseToken, result? })` fence expired/stale owners. Leases default to 30 seconds, bounded between 1 second and 5 minutes, using the database clock.
- Exported `enqueue(tx, { organizationId, applicationId, id, kind, idempotencyKey, payload? })` commits job plus outbox inside the caller's business transaction. `completeJob(tx, { organizationId, jobId, leaseToken, result? })` allows deterministic effects and completion to commit together. Persist effects under unique stable identities; a lease does not make a remote side effect exactly-once.
- `runs.start({ organizationId, applicationId, jobId, leaseToken })` requires a claimed investigation job and returns `{ runId, deadline }`. Retries return the same run and deadline. `runs.load({ organizationId, runId })` returns its private checkpoint and counters.
- `runs.checkpoint({ organizationId, runId, expectedVersion, checkpoint })` returns `{ version }`; optimistic concurrency fences stale updates and limits checkpoints to 32 KiB. The gateway derives scope from its authenticated run capability, never from arbitrary agent-supplied IDs.
- `runs.consumeTool({ organizationId, runId })` reserves one of eight tool calls. `runs.reserveModel({ organizationId, runId, reservationId, maxCostMicros })` requires external-processing opt-in, a live five-minute deadline, at most four calls, and available organization budget. Call before provider I/O. A reused reservation ID fails as `reservation_exists`, requiring reconciliation, never a repeated model call.
- `runs.settleModel({ organizationId, reservationId, actualCostMicros })` settles once, idempotently for the same amount. Unknown outcomes retain their full reservation across restarts. The gateway must reserve an actual worst-case charge and bound provider tokens/prices; an overrun fails and requires operator reconciliation. `runs.finish({ organizationId, runId, outcome })` accepts `succeeded | unavailable | failed` and refuses unsettled reservations. Declining opt-in or exhausting budget does not block deterministic event processing.

## Proposal and executor contract

`proposalSchema`, `proposalEligibilitySchema`, `verifiedStepUpSchema`, and their derived TypeScript types are exported. `Clock.now(): Date` is injectable for authentication/freshness tests; production must use a trustworthy server clock.

`proposals.create({ organizationId, proposal })` is a **trusted preparation-service method**, not a public model-output endpoint. It returns `{ proposalId, actionHash, recoveryEpoch }`. Typed proposals bind organization/application, allowed adapter, repository/branch, full base/candidate commits, increasing patch/minor dependency versions, artifact identity/digests, evidence provenance, policy version, test attestations, and an exact verification plan. `hashProposal(proposal, recoveryEpoch)` hashes canonical JSON with a versioned domain prefix. Identical proposals within an epoch return the same identity. Only invalidation metadata is mutable.

Inject `ProposalVerifier.verify(proposal, { phase: 'proposal' | 'approval' | 'execution' })` as an independent trusted service that inspects current policy, provider head, immutable artifacts, and scanner/test attestations. It returns fresh facts binding the exact commits, digests, attestation IDs, and policy plus required rescan, relevant suite, VM isolation, and repository automation-safety checks. The default is unavailable. Returning flags from an HTTP request or model output is not verification. Observing a changed head, changed artifacts/policy, or failed eligibility persists proposal invalidation before returning the rejection; a later head reversion cannot revive approval.

`proposals.approve(identity, { organizationId, proposalId, actionHash, stepUpProof })` returns `{ approvalId, expiresAt }`. Owner membership is row-locked against revocation. Inject `StepUpVerifier.verify({ proof, userId, organizationId, actionHash })`, validating an actual server-issued WebAuthn/TOTP second-factor ceremony. The returned `proofId`, identity/action binding, authentication/expiry times and method come from trusted verifier state. Proof IDs are single-use. Caller-supplied timestamps and extra keys are rejected. Proof freshness and approval lifetime are at most five minutes. Without this verifier approval is disabled.

The separate executor uses `executions.claim({ organizationId, approvalId })`, returning `{ executionId, claimToken, actionHash, proposal, recoveryEpoch }`. It rechecks current owner membership, proof-derived expiry, action hash, recovery state, independent policy/tests and provider head, then atomically consumes approval and claims a unique execution. Call `executions.assertWritable({ organizationId, executionId, claimToken })` immediately before provider I/O; it checks membership, expiry, recovery, and current proposal eligibility again. Use `executionId` for provider reconciliation/idempotency. `executions.finish({ organizationId, executionId, claimToken, outcome, providerReference? })` records `succeeded | failed | uncertain`; succeeded requires a provider reference. This records the adapter's outcome, not a claim of independent post-write verification.

There is no automatic execution reclaim: a crash or uncertain provider result requires reconciliation. This ledger cannot make Postgres and a remote provider atomic. A real GitHub adapter must demonstrate race handling, exact artifact publication, reconciliation, and post-write verification before enabling writes. No provider write API is implemented in this package.

## Database, recovery and checks

`createDatabase` exposes `tenant(organizationId, fn)`, intake-only `integration(integrationId, fn)`, `checkHealth()`, and `close()`. Context is parameterized and transaction-local. Runtime logins are rejected if privileged, if they own a Gotchu object, or if they belong to multiple service roles. Customer tables FORCE RLS and enforce tenant-aware foreign keys. See `packages/database/README.md` for operator-only provisioning/migration/recovery helpers.

Writes start frozen. Following restore, stop executors and call `setRecoveryState({ connectionString: operatorUrl, mode: 'freeze' })` before restarting them. This advances the epoch and invalidates old approvals. Unfreeze only after external execution identities have been reconciled using `mode: 'reconciled', reconciliationReference`. This is an explicit operations gate, not a proven restoration procedure.

Commands after installing workspace dependencies:

```sh
pnpm --filter @gotchu/contracts build
pnpm --filter @gotchu/database build
pnpm --filter @gotchu/backend build
pnpm --filter @gotchu/database typecheck
pnpm --filter @gotchu/backend typecheck
pnpm --filter @gotchu/backend test
pnpm --filter @gotchu/database test:postgres
```

The last command creates its own `postgres:17-alpine` container, random loopback port and random credentials, uses temporary storage without existing volumes, runs both packages' live tests, and removes that container. Alternatively set `GOTCHU_TEST_DATABASE_URL` to an operator connection for a disposable database named `gotchu_test_*`. Without it, live suites are explicitly skipped. MFA/eligibility unit fixtures do not prove real MFA, scanners, VM isolation, or provider integration; live database tests prove the ledger and persistence behavior against Postgres.

Remaining release gates include production credential-store/MFA/verifier adapters, trusted run-capability routing, provider concurrency/reconciliation and verification, measured quotas/retention, migrations/provisioning in deployment, external backups/restoration drills, and live VM isolation. Customer code and production provider writes remain disabled.

## Customer application service (version 2)

`createBackend({ database, customerDnsVerifier? }).customers` owns the authenticated customer workflow. Pass only a trusted server `Identity` derived from Auth.js (including `credentials:<uuid>` or an OIDC identity); never accept a user ID from HTTP input. The reserved demo principal is rejected. Customer methods accept `(identity, input)` except coordinator-only `pendingOrganizations({ limit? })`, `getRequest(claim)` and `recordResult({ input, leaseToken, report })`.

- `pendingOrganizations({ limit? })` → `string[]` is coordinator-only discovery of organizations with queued/running version 2 audit jobs, ordered by oldest job. Default 100, maximum 500. Uses a narrow SECURITY DEFINER function in zero UUID context; the API role has no execution grant. Hosts may opt in to dynamic assignment; static organization assignment remains the default host behavior. Every discovered job still requires scoped lease validation.
- `listWorkspaces(identity)` → `CustomerWorkspace[]`; `createWorkspace(identity, { name })` → `CustomerWorkspace`. Atomic owner bootstrap, at most 5 workspaces per identity, unique workspace name per identity. Discovery uses narrow SECURITY DEFINER functions through the zero UUID tenant context; runtime roles never bypass RLS.
- `listApplications(identity, { organizationId })` → `CustomerApplication[]`; `createApplication(identity, { organizationId, name })` → `CustomerApplication`; `updateApplication(identity, { organizationId, applicationId, name?, archived? })` → `CustomerApplication`. Owners/operators write; members read. At most 20 applications per workspace.
- `enrollTarget(identity, { organizationId, applicationId, origin, authorized: true })` → `{ target: CustomerTarget, challenge: { name, value, expiresAt } }`. One target per application, renewal replaces the challenge and increments its version. Challenge expires in 30 minutes. Return the generated token only here, retain only its SHA-256 hash. Consent binds the canonical HTTPS origin, actor and time.
- `listTargets(identity, scope)` → `CustomerTarget[]`; `verifyTarget(identity, { ...scope, targetId })` → `CustomerTarget`; `revokeTarget(identity, { ...scope, targetId })` → `CustomerTarget`. Verification lasts 7 days. The trusted injected `CustomerDnsVerifier` is `{ resolveTxt(name: string): Promise<string[][]> }`, compatible with Node DNS TXT chunks. Backend requests exactly `_gotchu.<hostname>`, joins chunks within each record, and compares the SHA-256 hash of the `gotchu-verification=<token>` token. No caller supplies verification results or tokens. The adapter must enforce a bounded DNS deadline and propagate unavailable errors; missing adapter returns 503. External HTTPS transport must independently reject private/reserved DNS addresses and redirects on every request.
- `uploadSource(identity, { ...scope, snapshot: { revision, files: [{ path, content }] }, authorized: true })` → `CustomerSourceSummary`; `listSources(identity, scope)` → `CustomerSourceSummary[]`. Immutable, server-digested JSON, at most 10 active snapshots per application and 100 new snapshots per workspace per rolling day (including deleted uploads), 1,000 files, 1 MiB per file and 4 MiB serialized snapshot. Normalized JS/TS/JSON/YAML/TOML paths only. No installation, execution, links, traversal, `.git`, `node_modules` or `.env` paths. Source is private Postgres JSON for local development.
- `deleteSource(identity, { ...scope, sourceSnapshotId })` → `void`. Owners/operators may delete an upload once no queued/running assessment references it. The upload body is removed, its id/digest remains as a tombstone for report foreign keys, and the active snapshot quota is released. Durable request/job inputs contain only source id/digest/revision pointers, so deletion erases the canonical raw upload. Reports retain bounded evidence excerpts, findings and the source digest for provenance. Re-upload creates a new snapshot id. Deletion also works on archived applications.
- `queue(identity, { ...scope, mode, sourceSnapshotId: string|null, targetId: string|null, idempotencyKey })` → `{ jobId }`. Source is required exactly for internal/both; a current verified target exactly for external/both. Admission is serialized per organization, at most 3 unfinished per application and 20 admissions per organization per rolling day. Exact retries precede quota checks; conflicts return 409 and quotas 429.
- `listReports(identity, { ...scope, limit? })` → `CustomerReportSummary[]`; `getReport(identity, { ...scope, reportId })` → `CustomerAssessmentReport`.
- `getRequest({ ...scope, jobId, leaseToken })` → `CustomerRunInput`; `recordResult({ input: CustomerRunInput, leaseToken, report })` → `{ reportId }`. Audit job payload is a compact version 2 `CustomerAssessmentIntent`, with no fixture revision or raw source. Its source is `{ id, digest, revision }|null`; `getRequest` materializes and digest-checks files from the one canonical snapshot under the current lease. Request includes application name, source `{ id, digest, revision, files }|null` and target `{ id, origin, version, verifiedAt, expiresAt }|null`. Report subject binds `{ sourceSnapshotId, sourceDigest, targetId, targetVersion, origin }`; report and job success commit atomically under a current scoped lease. Archive, target revocation/expiry/version drift reject completion.

Target revocation and re-enrollment (including renewal or changing origin) reject with HTTP 409 `target_assessment_in_progress` while any request for that target has a queued/running job, or a failed job whose `result.reasonCode` is `assessment_reconciliation_required`. The check and mutation hold the same exclusive organization/application locks as queue admission and `getRequest`; jobs are joined on organization, application and job identity. Lease expiry does not release this gate. Rejection leaves target status, version and authorization unchanged: **authorization remains active; retry once outstanding work finishes or an operator reconciles uncertain work.** It does not acknowledge revocation, cancel an assessment, extend authorization expiry or schedule a later revocation. Source-only jobs do not block target changes. Once work is settled, successful revocation prevents new external admission and `getRequest` still checks fresh target state and the current job lease.

The coordinator must retain ownership until runner work has fully settled, or quarantine uncertain execution with `assessment_reconciliation_required`. A transport error, timeout, lost lease or dead coordinator cannot prove remote scanner cleanup. Quarantined failed jobs keep target changes blocked even though their job state is terminal. Recovery requires trusted operator review establishing that all associated scanner/runner work has stopped before reconciling the durable job; do not clear quarantine or mark stale work terminal merely because its lease expired. There is no customer HTTP escape or automatic quarantine expiry. The real-Postgres backend tests use synthetic DNS/reports and explicitly labeled operator SQL bypass/reconciliation fixtures; they verify locking and defensive authorization, not remote runner cleanup.

Runtime schemas/types are exported by `@gotchu/contracts` from `customer-assessment.ts`; shared report refinements preserve the original finding/evidence/comparison invariants without projecting version 2 into a fixture report. Reports remain observation-only and are capped at 1 MiB. Model processing, MFA approvals, provider writes and customer-code execution are not enabled by this service. Schema migration: `006_customer_applications.sql`; the Auth.js account store is a separate integration.

## Operations monitoring integration

`@gotchu/contracts/operations.ts` defines the integration seam (exported through package root). The `backend.operations` service provides:

- Customer: `getConfig(identity, scope)`, `configure(identity, MonitorConfigInput)`, `listAlerts(identity, { ...scope, limit? })`, `getCoverage(identity, scope)`, `updateAlert(identity, { ...scope, alertId, state: 'acknowledged'|'resolved', resolution? })`.
- Trusted coordinator: `claimDue({ limit?, leaseMs? }) -> MonitorWork[]`; `materialize({ ...claim, repositorySnapshot?: CustomerSourceSnapshot }) -> { jobId: string|null }` atomically creates the existing customer audit request/job/outbox, with the configuring member's current Owner/Operator membership checked. Use standard jobs.claim and customers.getRequest for scanner/adapter hydration; do not construct run inputs or target URLs from HTTP/model data. `getWatch(claim) -> MonitorWork` rechecks active configuration and scope before adapter reads. `heartbeatRun({ ...claim, leaseMs? })` renews a current lease (1–300 seconds; default 300 seconds). `finishRun({ ...claim, status: 'completed'|'degraded', reason? })` settles scheduling work. Due scheduling has a 1–24 hour interval and shares existing assessment admission quotas (20/workspace/day); quota failure must be shown as degraded, not successful monitoring.
- Trusted coordinator: `recordObservation(RecordOperationObservation) -> { observationId, alertId: string|null }`, idempotent per application key. `basis` is either a live monitor run/lease, an existing report ID, or 1–100 persisted authenticated event IDs. Signed event aggregation supplies typed metrics; repository/provider observations supply checksummed adapter provenance. Caller HTTP attestations never use this method. Upstream status does not verify application impact; traffic volume alone does not establish attack or justify a load balancer.
- Customer plans: `createPlan(identity, OperationPlanRequest)`, `listPlans(identity, scope)`, `requestPreparation(identity, OperationPlanBinding)`, `attestStep(identity, { ...binding, key, attestation })`, `checkReadiness(identity, binding)`, `requestExecution(identity, binding)`. Revisions and hashes bind exact nonwriting preparation; attestations are explicitly self-reported. Execution always fails closed until separate trusted capability, MFA, exact proposal, preflight and executor adapters exist. No plan can become approved/executed through these methods.

The parent HTTP/coordinator stream owns routing and loop scheduling; the monitoring adapter stream owns repository/provider reads. `recordObservation` is never a customer HTTP endpoint. Only in-app alerts are delivered by this domain; configured signed-event telemetry, external notifications, provider impact verification and production recovery are separate capabilities.

Monitor config explicitly selects `providers: ('cloudflare'|'railway')[]` (default empty), an opaque operator-scoped repository key, a fixed source snapshot, and/or a currently verified target. Optional repository snapshots are accepted only from the trusted materializer when that run selected a repository key; they use the existing canonical digest, deduplication, ten-active-snapshots and 100-uploads/workspace/day bounds. Identical source bytes can be reassessed for new advisories on later runs. Materialization copies the current target scan profile when migration 010 supplies it and binds the persisted target version. Repository snapshots, request, job and canonical outbox are committed together. An exact run retry returns its job; a different repository digest conflicts.

`OperationCoverage` / `operationCoverageSchema` describe `getCoverage`: config, status (`not_configured | pending | active | degraded | stale`), current scope validity, last run (run/job IDs, status, reason, timestamps), fresh/stale observation counts and limitations. This is scheduled coverage only; it does not claim real-time telemetry or universal surface/repository coverage. `coverage_check` records an actual healthy adapter/report read without creating an alert. `coverage_gap` remains alertable. Successful finish requires retained observation evidence or a successful canonical assessment/report; absence of evidence cannot become completed monitoring.

For events, evidence reference is the persisted event UUID and checksum is its stored payload hash. For assessments, reference is the report UUID and checksum is SHA-256 of `canonicalJson(report)`; the coordinator must derive it from the stored report. Event/report references must belong to the exact application and be no older than 24 hours. New observations have at most 24 hours of freshness; evidence adapters provide checksums, collection time and tool/version. Repository/provider evidence requires a current monitor run lease. `upstream_outage` always retains `upstreamImpact: 'unverified'`. `traffic_pressure` requires persisted event IDs and typed measured metrics, and capacity plans require errors, latency above 1,000 ms or capacity above 80%; request volume alone does not justify load balancing or establish attack. `application_error` and `security_finding` support nontraffic assessment/event alerts. Resolving an alert records customer triage, not independently verified remediation.

Storage is admission-bounded: 1,000 retained monitoring runs per app (then scheduling disables), 2,000 observations per app, 100 observations per app per rolling day, and 100 plans per app. Evidence and plans have no customer deletion bypass; operator retention/archival maintenance remains required for long-running use. A config change cancels queued scheduled jobs only after active adapter leases settle/expire; running or uncertain scanner work blocks configuration and archive changes with `monitor_work_in_progress`. Authorization remains active on that rejection. HTTP adapters should map the same SQL trigger error on application archive to 409. Scheduled job claims independently recheck the monitor revision and configuring member's write membership. Revoked/expired targets and deleted sources cannot be materialized or hydrated as new monitoring work. No coordinator-wide membership or customer source/request write grant was added.

Migration 009 contains the service-only discovery/materialization/heartbeat functions and FORCE RLS tables. Real-Postgres tests use isolated cached `postgres:17-alpine` and synthetic adapter evidence, DNS-independent target fixtures and persisted-event fixtures; they establish database/authorization behavior, not actual repository/provider traffic, event signing, MFA, live cloud resources or production recovery. Existing event-authentication and proposal suites remain separate checks. Plans are nonwriting advisory artifacts with exact revision/hash binding; caller checklist attestations remain `self_reported`, and request execution always returns `operation_execution_unavailable` with required capability, independent preflight, exact proposal, MFA and executor gates.

Migration 013 settles invalid scheduled assessment claims and their monitor runs atomically. `jobs.claim` returns `null` when the authorization fence settles a job. A previously queued job with zero attempts fails with `monitor_authorization_changed`, releases its active assessment slot and allows source erasure. A prior running/requeued attempt fails with `assessment_reconciliation_required`; target revoke/renew and monitor changes remain blocked until reconciliation. Settlement grants no new I/O permission and does not refund the rolling admission quota.

## Private correction candidates

`createBackend().corrections` uses the server-only `@gotchu/scenarios/server` recipes and public `@gotchu/scenarios/contracts` response schemas:

- `recommendations(identity, { organizationId, applicationId, reportId }) -> ReportRecommendationsResponse`: members including viewers may read evidence-bound recommendations. External-only reports need no source. The stored report, original durable request/job and source digest are checked; this does not require a current scanner lease or renew target authorization.
- `prepare(identity, { organizationId, applicationId, reportId, recipeId, findingId, expectedSourceDigest }) -> PrepareCorrectionResponse`: owners/operators only. Returns `{ sourceId, jobId, changes: [{ path, description }], patchHash }`, never source snippets. Creates a private immutable corrected snapshot and queues an independent **internal** assessment in one transaction through existing customer admission/outbox services. No repository/provider/production changes, tests or customer-code execution occur. The original snapshot remains unchanged.

Both operations reject the reserved demo principal, wrong tenant/application and archived applications. Deleted original source returns 409 `source_unavailable`; `customers.getReport` still reads its historical report. Digest drift returns 409 (`expected_source_digest_mismatch` or `assessment_scope_mismatch`); unsupported preparation returns 409 with the recipe's blocked reason, including `recipe_requires_integration`. Preparation never promotes integration-required recipes to patches. The deterministic `correction:<patchHash>` key returns the same source/job before quotas, including after a completed candidate is deleted; replay does not resurrect deleted bytes. A deleted original still prevents preparation/replay. Source admission, canonical job/request, outbox and metadata-only audit commit or roll back together. Audits contain recipe/report/finding/source IDs, patch hash, path and checksums, never before/after source content. A queued rescan is not evidence of a verified correction; scanner integration and report interpretation remain separate.
