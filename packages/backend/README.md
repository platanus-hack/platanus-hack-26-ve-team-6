# Backend integration contract

Framework independent domain services for TanStack Start/Auth.js, durable coordinators, and the separate executor. This contract is being implemented in this worktree; the final exports and tests are authoritative.

- `@gotchu/database`: `createDatabase({ connectionString, role, max? })`, `database.tenant(organizationId, fn)`, `database.integration(integrationId, fn)`, `database.close()`, `migrate({ connectionString })`. Transactions use one checked-out connection and transaction-local, parameterized context. Roles: `gotchu_api`, `gotchu_ingest`, `gotchu_coordinator`, `gotchu_executor`; provision distinct logins with only the appropriate role. Never use the migrator/superuser connection at runtime.
- `@gotchu/backend`: `createBackend({ database, credentials?, clock?, stepUpVerifier?, proposalVerifier? })`. Create separate instances with the correct database role for each process. No HTTP framework or provider write implementation is included.
- `backend.events.ingest({ integrationId, timestamp, signature, rawBody })`: `rawBody` is a Buffer of exact received bytes. HMAC-SHA256 input is `gotchu-events-v1\n${integrationId}\n${timestamp}\n` followed by raw bytes, signature is lowercase hex. Timestamp is Unix seconds. Derives tenant/application from active integration, validates `eventBatchSchema`, durably commits event/job/outbox, and returns `{ accepted, duplicates, jobId }`. HTTP adapters must bound streaming input before buffering. CredentialStore resolves an opaque reference; no plaintext signing secret is stored in customer-readable tables.
- `backend.web`: `authorize(identity, organizationId, roles?)`, `queueAudit(identity, { organizationId, applicationId, idempotencyKey })`, `getJob(identity, { organizationId, jobId })`, `listApplications`, `listIncidents`, `getCoverage`, `listProposals`. `identity = { userId }` must come from a verified server-side Auth.js session. Client-selected organization IDs are selectors, never authorization. No identity headers are supported.
- `backend.outbox`: `claim({ organizationId, limit?, leaseMs? })`, `delivered({ organizationId, id, leaseToken })`. Publish the returned `JobEnvelope` using its stable `id`, then mark delivered. Crash after publish may repeat delivery.
- `backend.jobs`: `claim({ organizationId, jobId, leaseMs? })`, `complete({ organizationId, jobId, leaseToken, result? })`, `heartbeat(...)`. Consumers persist effects and completion transactionally via `database.tenant`; they must use stable effect IDs. Expired leases are fenced by fresh tokens.
- `backend.proposals`: `create({ organizationId, proposal })`, `approve(identity, { organizationId, proposalId, actionHash, stepUpProof })`. Exact typed proposals are immutable, hashed canonically, and require an injected independent `ProposalVerifier`. StepUpVerifier accepts an opaque proof and checks a server-issued authentication ceremony bound to user, organization, and exact action hash. Caller timestamps never establish step-up. Proof IDs and approvals are one-use with expiry.
- `backend.executions`: `claim({ organizationId, approvalId })`, `finish({ organizationId, executionId, claimToken, outcome, providerReference? })`. Claim rechecks membership, exact hash, policy/tests, base head, expiry and recovery epoch through the trusted verifier. Durable claims are never automatically retried after an uncertain provider result. Provider writes belong to the independent executor adapter and must reconcile by execution ID.

`Clock.now(): Date`, `CredentialStore.getSigningSecret(reference): Promise<Uint8Array>`, and verifier interfaces are exported. Domain failures use `BackendError` with `code` and `status`. Missing trusted verifiers disable sensitive capabilities. Integration credentials and private agent checkpoints are excluded from customer projections. Customer-code execution and live GitHub writes are not implemented or claimed.

Migration command: `GOTCHU_MIGRATION_DATABASE_URL=... pnpm --filter @gotchu/database migrate` (after builds). Live tests require `GOTCHU_TEST_DATABASE_URL` pointing to a dedicated disposable database; otherwise they are explicitly skipped. Do not point live tests at customer data.
